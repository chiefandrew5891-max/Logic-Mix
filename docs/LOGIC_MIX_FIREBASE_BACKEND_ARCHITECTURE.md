## 1. Executive Summary

- Клиент сейчас полностью автономен: нет сети, нет `INTERNET`, нет JSON/сериализации, нет WorkManager. Задания — зашитый Kotlin, txt-словари и детерминированные генераторы.
- Рекомендуемая модель — **«контент-пакеты + манифест»**: сервер раз в период собирает проверенные задания в компактные JSON-пакеты (gzip) в Cloud Storage, клиент скачивает манифест и только изменившиеся пакеты. Firestore — каталог/аудит, а **не** то, что читает каждый клиент.
- Генерация и тяжёлая валидация — **Python на Cloud Run Jobs** (запуск Cloud Scheduler). Cloud Functions (TypeScript, 2nd gen) — тонкий API и триггеры. Публичный API клиента — по возможности просто статические файлы (CDN-кэшируемые) из Storage, без вызова функций.
- Категории делятся на три класса:
  1. **Языковые пакеты с сервера** (§0): Word Search (словари), Mini Crossword (слова + определения), Word Logic (слова, категории, связи).
  2. **Локальная генерация на Android**: Matchstick, Number Sequence (расширяется до Number Logic), Visual Logic (расширяется семействами), Sudoku, Orb Lines, Two Dots. Серверный каталог математических и визуальных задач не строится.
- Главные риски: ключ прогресса по индексу уровня в 3 категориях; два разных «пространства» ID; языковое качество; отсутствие в клиенте любой сетевой инфраструктуры; пересчёт отдельных скрытых зависимостей (подсказки, XP).
- Минимальный старт: Firestore + Storage + Scheduler + один Cloud Run Job + Remote Config. Plan Blaze, скорее всего, понадобится (Cloud Run/Scheduler/Secret Manager/Functions 2nd gen) — проверить в документации; поставить бюджетные алерты.

## 0. Мастер-промпт v3 (2026-11-22) — наивысший приоритет

Эта редакция **отменяет** предыдущие версии там, где они противоречат. Порядок источников требований: мастер-промпт → фактический код → прежние документы (справочно).

**Изменения относительно v2:**
1. Backend — прежде всего **конвейер языковых данных** (слова, определения, формы, частотность, семантика) → пакеты → публикация. Серверной генерации математических и визуальных задач **нет**: NUMBER_SEQUENCE, MATCHSTICK, VISUAL_LOGIC, SUDOKU, ORB_LINES, TWO_DOTS генерируются локально на Android. Прототип на числовых последовательностях (план v2) **отменён**; такие задания допустимы только как тестовые fixtures.
2. Языков интерфейса **восемь**: en, ru, uk, it, de, fr, es, zh-CN. Конфиг языков (`backend/logicmix_backend/languages.py`) расширяется без изменения ядра; `zh-CN` для `WORD_SEARCH`/`MINI_CROSSWORD` недоступен (клиентский `CategoryAvailability`, на сервере флаги `wordsearch=false`, `crossword=false`). Первый импорт — en и ru.
3. Подтверждение перед этапами B–D не требуется. Ограничения на облачные ресурсы/платные операции/секреты сохраняются.
4. Firebase / Google Cloud — утверждённая целевая платформа. Объекты (пакеты) — Cloud Storage; Firestore — только метаданные и не читается клиентом; не используется для хранения словарей.
5. Три независимые подсистемы: (A) локальный игровой движок (офлайн-first), (B) контент-backend, (C) монетизация (отдельно).

### 0.2 Источники (реестр `registry.py`)

Приоритеты: 1 Kaikki.org/Wiktionary (слова, леммы, POS, определения, формы) · 2 Wikidata (категории, связи) · 3 LibreOffice Dictionaries (орфография, формы) · 4 wordfreq (частотность, сложность). Источники **не взаимозаменяемы**: слова создают только словарные источники; частотность и Wikidata дополняют существующие записи. Все четыре помечены `needs_review`: лицензии (в частности ShareAlike у Wiktionary-данных; лицензии отдельных словарей LibreOffice; условия данных wordfreq) **не проверены**, коммерческое использование не установлено. Публикация в `production` технически блокируется (`Publisher.production_blockers`), пока источник не переведён в `approved` с датой проверки. Атрибуция входит в каждый пакет (`attribution`), удалять её нельзя. Единственный `approved` — собственные fixtures (только для тестов/staging).

Состояние на 2026-11-22: реальная загрузка Kaikki **не выполнена** — хост `kaikki.org` недоступен из среды разработки; адаптеры проверены на fixtures.

### 0.3 Реализованный backend (`backend/`)

Реализовано и покрыто тестами (`python3 -m unittest discover -s tests -t .`, 27 тестов): реестр источников; адаптеры Kaikki JSONL, Hunspell `.dic`, TSV частот, Wikidata JSONL, fixtures; сетевой слой (timeout, retry с exponential backoff, rate limit, лимит размера); нормализация (NFC, алфавит по языку, блок-лист, отсев словоформ); дедупликация и слияние; SQLite-хранилище с изоляцией сбоев и «последней успешной версией»; обнаружение неизменившегося источника; классификация пригодности по играм; сборка детерминированных gzip-пакетов с SHA-256; валидатор пакетов; манифест; публикация «файлы → манифест последним», откат, каналы staging/production, статусы `draft→generated→validated→approved→published` + `retired`; эталон клиентского протокола синхронизации (Python); точка входа Cloud Run Job; шаблоны Dockerfile, job, scheduler, правил Storage/Firestore (**не применены**).

Не реализовано: реальный импорт (сеть/лицензии), адаптер разворачивания аффиксов Hunspell, семантическое обогащение Wikidata (адаптер читает уже подготовленную выгрузку), `LanguageReviewer`, облачное постоянное состояние (SQLite в Job временный: durable-состояние хранить в Storage — задача этапа E), любой Android-код.

### 0.4 Формат пакета (по факту реализации)

JSON (`sort_keys`, компактный) → gzip (`mtime=0`, воспроизводимо). Поля: `schema`, `packId` (`<type>-<lang>`), `type` (`wordsearch|crossword|wordlogic`), `language`, `dataVersion`, `publishedAt`, `minClientVersion`, `sources`, `attribution`, `limits`, `rows`. Строки — массивы (без повторения ключей): wordsearch `[WORD, tier]`; crossword `[WORD, clue, tier]`; wordlogic `[WORD, categories, relations]`. SHA-256 (gz и raw), размер и путь — в манифесте. Файл пакета неизменяем: `packs/<id>/<version>-<sha12>.json.gz`, `Cache-Control: immutable`; манифест — `no-cache`; история манифестов — в `private/` (закрыта правилами). На тестовых fixtures сжатие даёт ~40% экономии; **реальные размеры будут измерены на настоящих данных**. Для очень больших словарей (сотни тысяч слов) JSON может оказаться тяжёлым — решение (индексированный бинарный формат) принимать по измерениям, не заранее.

### 0.5 Mini Crossword — строгий потолок 10 слов

Факт по коду: сейчас кроссворды — 5 готовых сеток на язык, генератора в клиенте нет; новые требования Android **не реализованы**. Требования: ≤ 10 слов в любой сетке, любой режим и сложность; количество слов меняется от задания к заданию (например 4, 7, 5, 9, 6, 10; без линейного роста до 10 и без «всегда 10»); диапазон ~3–10; сложность — длина слов, пересечения, плотность, сложность определений, открытые буквы, тематика, подсказки (в среднем растёт, не монотонно). Генератор: слова и определения выбранного языка из пакета, корректные пересечения, связность, нумерация, воспроизводимость по seed, лимиты времени/памяти, fallback на ранее проверенную сетку; тест на массовой генерации с проверкой `≤ 10`. Потолок продублирован в пакете (`limits.crosswordMaxWords`). UI: независимые pan/zoom игровой поля (диагональное перемещение, pinch-zoom, пределы масштаба, сброс, «показать всё», корректный hit-test при масштабе, внешний scroll страницы работает, масштаб не сбрасывается при вводе, клавиатура); состояние хранит ID, `dictVersion`, буквы, выбор слова. Реализация — отдельная Android-задача (требует Android SDK).

### 0.6 Visual Logic и Number Logic — локальное расширение (задачи Android, не начаты)

- Visual Logic: семейства — матрицы 2×2/3×3, вращение, отражение, силуэты, абстрактные узоры, ключ и замок, недостающий фрагмент, пространственное мышление, складывание бумаги, развёртки кубов, наложение/исключение, лишний элемент, последовательности. Процедурно, Canvas, оригинальные примитивы. Каждое семейство: формальные правила, независимый верификатор уникальности правильного ответа (неправильные варианты не подходят), отсев визуально одинаковых, seed и параметры в задании; управляемое распределение семейств (не много одинаковых подряд).
- Number Logic: внутри существующей категории `NUMBER_SEQUENCE` (ID и сохранения не меняются) — последовательности, порядок действий, скобки, пропущенные операторы, пирамиды, матрицы, весы, закономерности, внимательность, смешанные. Выражения через синтаксическое дерево, ответ вычисляется независимо от отображения, без деления на ноль и непредусмотренных дробей, единственность ответа, сложность — не только величина чисел.
- Matchstick: проверить, ограничен ли генератор 60 уровнями (по коду уровни строятся `MatchPuzzles.build` от индекса); существующие 60 не менять.
- Sudoku, Orb Lines, Two Dots: не переносятся на сервер; менять только при найденных ошибках.

### 0.7 Монетизация (отдельная подсистема, не реализована; AdMob в проекте нет)

Границы будущей интеграции: Google AdMob через официальный SDK; rewarded-реклама — добровольная, награда только по подтверждённому событию SDK (при необходимости серверная проверка SSV); предзагрузка средствами SDK; игра не блокируется при отсутствии рекламы или сети; запрещены запись рекламных роликов для офлайн-показа и самодельные отчёты о просмотрах; монетизация не зависит от контент-пакетов; текущие правила XP/наград не меняются.

### 0.8 Синхронизация Android (подготовка; Android не изменён)

Эталон протокола — `client_reference.py`: проверка манифеста ~раз в 24 ч через WorkManager (ограничение «есть сеть»; запуск может быть отложен системой — корректно обрабатывать), дополнительная проверка при запуске при давности > 24 ч; загрузка только пакетов своего языка и только изменившихся (sha/версия); проверка SHA-256, схемы и `minClientVersion`; атомарная установка (tmp → replace, указатель последним); при сбое остаётся прежний пакет; **подмены языка нет**; пакеты, на которые ссылаются незавершённые игры, не удаляются; `dictVersion` закрепляется за началом уровня Word Search; встроенные 12 уровней и словари не меняются; Room-миграции (если понадобятся) — явные и с тестами, без destructive migration; одно начисление XP за уникальный ID.

### 1b. Решение №1 (пересмотрено) — китайский язык сохраняется

Прежнее решение об удалении `zh-CN` **отменено**. Приложение сохраняет **8 языков интерфейса**: `en`, `ru`, `uk`, `it`, `de`, `fr`, `es`, `zh-CN`. Китайские ресурсы, переводы, настройки и локализация не удаляются.

Правила (код пока не трогаем — только документация):
- При выбранном китайском языке категории `WORD_SEARCH` и `MINI_CROSSWORD` **полностью скрываются** из каталога. Проверено: сейчас это делает `domain/content/CategoryAvailability.kt`; он остаётся единым механизмом для всех игровых режимов и экранов (главное меню, Daily, будущие списки). Любое новое скрытие категории делается только там.
- Остальные категории остаются доступными (нейтральные: числа, спички, визуальная логика, Sudoku, Orb Lines, Two Dots).
- `WORD_LOGIC` не удаляется и не скрывается автоматически. Отдельно исследуется адаптация словесных аналогий и других заданий под китайский язык (🔍 исследование, результата нет, сроков нет). До его завершения подмена английскими заданиями запрещена (решение №2): при отсутствии китайского пака показывается локализованное сообщение «нет заданий для этого языка».
- Серверные контракты: языки интерфейса — 8; **контентные** языки словесных категорий — те, для которых есть проверенный контент. Для `zh-CN` словесный контент пока отсутствует. Код `zh-CN` допустим в схемах и манифесте, пакетов для него нет.
- Первый backend-прототип — только `ru` и `en` (решение №3).
- Проверено по коду: `AppLanguage.CHINESE_SIMPLIFIED`, `ContentLanguage.ZH_CN`, `LetterKeyboard` (пустая раскладка для zh), `SettingsScreen` (`language_name_zh`), `locales_config.xml`, `values-zh-rCN` — всё остаётся без изменений.

### 1c. Решение №2 — контент на выбранном языке

Контракт выбора контента для словесных категорий (WORD_LOGIC, MINI_CROSSWORD, WORD_SEARCH):
1. Пакет языка L из кэша (скачанный и проверенный) → иначе
2. встроенный пакет языка L → иначе
3. локализованное сообщение «Для этого языка заданий пока нет» (категория остаётся видимой или скрывается — решение UI, но **EN/RU не подставляются**).

**Проверено — расхождения с решением:**
- `WordLogicPacks.resolve()` для языков без пака возвращает EN и `isFallback = true` (паки только RU и EN). Нарушает решение №2 для uk, it, de, fr, es.
- `ContentLanguage.forInterface` падает в EN для неизвестного языка; для `zh-CN` Word Logic пака нет — нужно сообщение вместо подмены (см. §1b).
- Кроссворды: 7 языков × 5 сеток есть; филворды: 7 txt-словарей есть; Word Logic: нужно создать uk, it, de, fr, es; для zh-CN — исследование адаптации.

Прогресс сохраняется отдельно на язык (ключи `mini_crossword_<tag>`, `ws.<tag>.*`) — смена языка не затирает прогресс другого языка (проверено). Для `word_logic` ключ **один на все языки** (`word_logic.level`, проверено) — при смене языка индекс уровня общий; это дефект относительно решения №2, нужно перейти на ключ с тегом языка (миграция, §«риски» плана).

### 1d. Решение №4 — Daily Challenges

Статус в клиенте (проверено): `GameMode.DAILY` есть; кнопка Daily на главном экране ведёт на «Coming soon»; `ProgressRepository.recordAttempt` начисляет XP только за `GameMode.CAREER`. **Daily не реализован.**

Проект модели (💡):
- Календарь: UTC. `dailyKey = yyyyMMdd` (UTC).
- Набор дня: по одному заданию на категорию-участницу (в первой версии — нейтральные: NUMBER_SEQUENCE, MATCHSTICK, VISUAL_LOGIC; позже языковые).
- ID daily-задания: `<cat>-[<lang>-]d-<yyyymmdd>` (например `ns-d-20261122`, `cw-ru-d-20261122`). **Отдельные ID**, не ID обычных заданий: иначе решение в Career блокировало бы XP в Daily и наоборот.
- Доставка: маленький файл `daily/<channel>/v1/<yyyymmdd>.json.gz` (несколько КБ), клиент предзагружает 7 дней вперёд вместе с проверкой манифеста; офлайн играет ранее загруженные дни.
- Детерминированный запасной вариант без сети: для Sudoku/Orb/Two Dots seed = функция от `dailyKey` (генераторы локальные и детерминированные — проверено: Sudoku `Random(seed*31+attempt)`, Orb свой `Roll`, Two Dots `kotlin.random.Random(seed)`).
- Награда: XP-транзакция по уникальному ключу `"$profileId:$dailyId:FIRST_SOLVE"` — тот же механизм идемпотентности, что и сейчас (проверено в `ProgressRepository`); серия посещений и бонусы — позже, отдельное решение. **Экономика наград не проектируется на этом этапе.**
- Точки интеграции в клиенте (будущие): разрешить `DAILY` в `ProgressRepository.recordAttempt`, экран Daily, хранение результата дня, `DailyRepository`.

### 1e. Решение №5 — Word Search: словарь против готовых полей

Проверено: клиент строит уровень из словаря: `WordSearchLevels.build(language, index, dictionary)`; `seed = "ws:<tag>:<index>".hashCode()`, слова = `dictionary.core` отфильтрованные по длине, `sorted().shuffled(Random(seed)).take(n)`. 4 тира × 3 уровня = 12 уровней на язык. `WordSearchStore` хранит `id`, `seed`, найденные слова (строками), подсказки.

| Критерий | Словари + локальный генератор | Готовые поля |
|---|---|---|
| Трафик | малый, один файл на язык, на много уровней | ≈ сотни байт на уровень |
| Воспроизводимость | зависит от версии словаря и алгоритма | абсолютная |
| Офлайн | да | да |
| Риск для прогресса | **высокий**: правка словаря меняет состав слов уровня с тем же индексом | нулевой |
| Нужна проверка на сервере | словарь + контрольная генерация | каждая сетка |
| Годится для Daily | нет (хотим гарантированный одинаковый результат у всех) | да |

**Решение:** гибрид. (а) Обычные уровни за пределами встроенных 12 — «словарь + генератор», при этом словарь **версионируется и закрепляется за уровнем** (`dictVersion` в метаданных уровня; встроенные 12 уровней продолжают использовать вшитый словарь — их менять нельзя). (б) Daily и спецзадания — готовые поля `placements` (формат §13). Генератор `WordSearchGenerator` не меняется (проверено: изменений не требуется). Что нужно клиенту: индексы уровней свыше 12 и выбор словаря по `dictVersion` — новый код, не реализован.

### 1f. Решение №7 — стандарт стабильных ID

Формат (💡, расширяет существующие префиксы клиента: `ns`, `matchstick`, `wl`, `cw`, `vl`, `ws`, `sudoku`, `orb`, `twodots`):

```
<cat>-[<lang>-]<origin>-<serial>
cat    : ns | matchstick | wl | cw | vl | ws
lang   : en | ru | uk | it | de | fr | es        (только для языковых категорий)
origin : x  = опубликовано сервером (обычный пул)
         d  = Daily
serial : x → 6 цифр (000001…), d → yyyymmdd (UTC)
regex  : ^(ns|matchstick|wl|cw|vl|ws)-(?:(en|ru|uk|it|de|fr|es)-)?[xd]-[0-9]{6,8}$
```
Примеры: `cw-ru-x-000123`, `wl-en-x-000007`, `ns-x-000001`, `ns-d-20261122`.

Правила:
- Встроенные ID (`cw-ru-01`, `ns-001`, `wl-en-03`, `vl-05`, `ws-ru-02`, `matchstick-7`) **не меняются** и не пересекаются с новыми (у новых есть сегмент origin).
- ID не содержит позиции в массиве; порядок выдачи хранится отдельно (`orderIndex` в пакете), его смена прогресс не ломает.
- Языковое задание = один язык; нейтральное (ns, matchstick, vl) — без языка, **один и тот же ID во всех языковых пакетах** (XP за него начисляется один раз на профиль независимо от языка интерфейса).
- Изменился смысл/ответ — новый ID, старый → `retired`. Правка опечатки без изменения решения — тот же ID, `contentVersion + 1`.
- Sudoku/Orb/Two Dots сохраняют текущие ID (`sudoku-<diff>-<seed>`, `orb-<seed>`, `twodots-<mode>-<id>`).
- Совместимость с индексными сохранениями (Crossword, Word Logic, Visual Logic, проверено: `<key>.level` — индекс в списке): эффективный список = `встроенные (неизменный порядок, N штук) + серверные по orderIndex, только дописываются`. Пока встроенный список неизменен и серверные только добавляются в конец, старый индекс остаётся верным. Переход на `firstUnsolved` по ID — рекомендуется, подробности в плане.

### 1g. Решение №10 — автоматический конвейер

Статусы: `draft → generated → validated → approved → published`, из любой стадии до `published` возможен `rejected`. **Расширение к списку владельца:** `retired` (снятие уже опубликованного; без него невозможен отзыв/откат). Статус `validation_pending` из v1 убран.

Три слоя проверки, каждый пишет результат в `puzzles/{id}.validation.checks[]`:
1. **Техническая:** JSON, схема, размеры полей, Unicode NFC и отсутствие управляющих/«битых» символов, язык по алфавиту, стабильность ID, дубликаты (fingerprint).
2. **Игровая:** решение существует и соответствует правилам клиента; для числовых рядов — единственность по реестру правил; для спичек — `minMoves == maxMoves`; для визуальных — ровно один вариант равен ответу; для кроссвордов — аналог `CrosswordPuzzle.problems()`; для филвордов — `WordSearchVerifier`-аналог.
3. **Языковая:** орфография по словарю, соответствие подсказки ответу, список нежелательных слов, алфавит. Интерфейс `LanguageReviewer` с **локальной заглушкой** (`NoopReviewer`: всегда «needs human review»); платная AI-модель не подключается без отдельного согласования; AI — не единственный источник истины.

`approved` достигается: автоматически для нейтральных категорий при полностью пройденных слоях 1–2; для языковых — после слоя 3 и (на первом этапе) выборочной ручной проверки владельцем на русском.

### 1h. Решение №11 — один проект, staging / production

- Storage: `public/staging/v1/…` и `public/production/v1/…`; Firestore: поле `channel: staging|production` в `packs`, `manifests/{channel}`, `puzzles`.
- Android: debug-сборка читает staging-манифест, release — production (канал зашит в `BuildConfig`, не в Remote Config, чтобы тестовый канал нельзя было включить случайно).
- Staging-контент не секретен (это головоломки); граница безопасности — **запись и публикация**: только сервисные аккаунты, у клиента нет прав записи, ключей админа в APK нет. Публичное чтение staging допустимо; если владелец захочет закрыть — потребуется Authentication/подписанные URL (отдельное решение).
- Публикация в production — только из staging-пакета с тем же sha256 («promote», без пересборки). Откат: манифест production снова указывает на предыдущий `packVersion`.

## 3. Проверка полноты и противоречий аудита

1. **Языки.** Запрос: 7 языков (en, uk, ru, it, es, de, fr). В клиенте `ContentLanguage` содержит **8** (добавлен `ZH_CN`); для zh-CN скрыты Word Search и Mini Crossword (`CategoryAvailability`). **Решено (№1, пересмотрено): `zh-CN` сохраняется, 8 языков интерфейса (см. §1b).**
2. **Реальное покрытие языков:** Word Logic — только RU и EN (остальные откатываются в EN, `isFallback`). Это нарушает требование «не EN при UK-интерфейсе» — уже существующий fallback, надо решить (раздел 12).
3. **Дублируются понятия «уровень» и «ID»:** три категории выбирают по индексу списка; две — по `solved_puzzles`. Единой модели нет.
4. **Аудит не фиксирует (нужны Kotlin-файлы):** точный формат `NumberSequencePack` (нужен для расчёта «обоснования» правил); таблица палитры цветов `Tile.color`; текст подсказок Visual Logic (по `rule`, не в задании); как `CategoryGames.store.levelIndex` ведёт себя при `index >= size` (есть: `allDone`).
5. **JSON-примеры в аудите** — предлагаемые, а не реальные. В примере спичек `startMask: 0` — заглушка; в архитектуре используем реальную 23-битную маску.
6. **Спички:** в модели нет `difficulty`; сложность = `maxMoves` (1 или 2). Типы задач кроме `A ± B = C` в клиенте **не существуют** → новых типов не вводим (требование «не вводить новые механики»).
7. **«Допустимые перемещения» (запрос 3.1)** клиент не хранит — выводятся движком. Хранить в пакете не нужно.
8. **Daily/Endless не реализованы** — серверный Daily пока только 💡.
9. **Нет версионирования состояния** (`encode()`-строки без версии, кроме `td1`) — меняя формат задания, нельзя ломать сохранённые состояния.
10. **Подсказки** Number Sequence и Word Logic лежат внутри задания, у остальных — вычисляются движком.

## 6. Схема Firestore (серверная)

Принцип: **документы маленькие, без массивов растущей длины, без чтения клиентом**.

- `puzzles/{puzzleId}` — каталог (1 документ = 1 задание, без payload, payload в Storage при публикации; для маленьких категорий допускается payload до ~50 КБ):
  `category, language|null, difficulty, schemaVersion, contentVersion, status, fingerprint, fingerprintAlgo, source{type, sourceId, licenseId}, generator{name, version, seed, params}, validation{status, validatedAt, validatorVersion, checks[]}, createdAt, publishedInPack|null, retiredAt|null, retireReason|null`.
- `fingerprints/{sha256}` → `{puzzleId, category}` — уникальность через транзакцию create-if-absent.
- `packs/{packId}` — `category, language, packVersion, schemaVersion, minAppVersion, count, sha256, sizeBytes, storagePath, status(draft|published|withdrawn), createdAt, supersedes`.
- `manifests/current` (и `manifests/history/{ver}`) — каноническая копия манифеста.
- `sources/{sourceId}` — `name, url, license, restrictions, retrievedAt, dataVersion, attributionRequired, robotsChecked`.
- `jobs/{jobId}` — журнал запусков: тип, категория, язык, счётчики generated/rejected/duplicate, длительность, ошибки; TTL-политика.
- `stats/{yyyymm}` — агрегаты по категории/языку (инкремент пакетно, не на каждое задание).
- `reviews/{id}` — очередь ручной проверки языковых заданий.

Индексы (составные): `puzzles(category, language, status, difficulty)`, `puzzles(status, createdAt)`, `puzzles(fingerprint)`, `packs(category, language, status, packVersion desc)`. Лимит роста: запись каталога — одна на задание; для генераторных категорий (Sudoku/Orb/TwoDots) каталог **не ведётся**.

## 10. Проверка решений

Принцип: **два независимых механизма** — (а) порт клиентской проверки (golden-тесты против Kotlin-результатов), (б) независимый решатель на сервере.

- Matchstick: брутфорс по `correctStates`; сравнение с `maxMoves`.
- Number Sequence: набор конкурирующих гипотез; решение должно воспроизводить все числа и давать ровно один ответ; ответ в диапазоне Int.
- Word Logic: структура (4 варианта, `correctId` ∈ options, дубли текста), лингвистические проверки словарём, ручное ревью.
- Crossword: буквы на пересечениях, алфавит языка (нормализация NFC, upper), отсутствие «случайных» слов, связность.
- Visual: исполнение правила → ответ; ровно один вариант совпадает.
- Word Search: путь по клиентским правилам (ортогональные соседи, без повторов), слова ≥3 буквы, нет неучтённых случайных слов из словаря (насколько возможно).
- Sudoku (если когда-либо понадобится): `countSolutions == 1`.

Статусы: `Draft → Generated → ValidationPending → Validated | Rejected → Approved → Published → Retired`. В пакет попадают только `Approved` (для кода-генераторных категорий без ручной стадии — `Validated` автоматом при включённом флаге доверия).

## 11. Импорт и дедупликация

**Источники:** A — собственные генераторы; B — открытые словари/корпуса (записывается лицензия, URL, дата, версия, атрибуция в `sources/`); C — ручной импорт JSON/CSV (тот же конвейер). Без скрейпинга сайтов; любой веб-источник — только после проверки лицензии/ToS/robots.txt и согласования (❓).

**Fingerprint (sha256 от канонической формы):**
- Number Sequence: `(sequence, answer)` + `ruleId`.
- Matchstick: `(startMask, maxMoves)`.
- Crossword: нормализованное множество `(row, col, direction, ANSWER)` + симметрии (поворот/отражение) → минимальное представление.
- Visual: `(rule, tiles, gapIndex, columns)` + множество options без учёта порядка.
- Word Search: `letters` + сортированные `placements`; доп. «мягкий» fingerprint — набор слов.
- Sudoku (если нужно): каноническая форма относительно перестановок цифр/строк/колонок/транспозиции (при честной оценке — приближённая; полная канонизация дорога).
Мягкая похожесть (набор слов у кроссвордов > порога) → флаг `nearDuplicate`, а не гарантия уникальности.

## 12. Локализация

- Языковая категория → `language` обязателен; один документ = один язык; сервер отклоняет символы вне алфавита языка (UK: і ї є ґ; RU: ё/ъ по правилам; de: ä ö ü ß; fr/es/it: диакритика).
- Нормализация: Unicode NFC, `uppercase` по локали (`ß`, `İ` — осознанные правила), без смешения скриптов.
- Словари: на язык отдельный файл с версией и лицензией; список запрещённых/нежелательных слов отдельно.
- Выбор клиентом: `ContentLanguage.forInterface(AppLanguage)`. 🆕 Контракт (решение №2, §1c): кэш языка → встроенный пак того же языка → локализованное сообщение. Подмена языка (в т. ч. на EN) запрещена.
- Качество: статус `Approved` для словесных наборов только после проверки носителем (CLI-выгрузка очереди `reviews`).
- zh-CN: интерфейс сохранён; WORD_SEARCH и MINI_CROSSWORD скрыты через `CategoryAvailability`; нейтральные категории доступны; WORD_LOGIC — исследование, без подмены на EN.

## 13. API-контракты (💡 новые)

Предпочтительно статическая раздача.

`GET /public/v1/manifest.json` (ETag)
```json
{
  "apiVersion": 1, "generatedAt": "2026-11-22T00:00:00Z", "manifestVersion": 17,
  "packs": [
    { "packId": "word_search-uk-0003", "category": "WORD_SEARCH", "language": "uk",
      "packVersion": 3, "schemaVersion": 1, "minAppVersion": 20, "count": 12,
      "sizeBytes": 18234, "sha256": "…", "url": "packs/WORD_SEARCH/uk/3.json.gz",
      "supersedes": 2, "status": "published" }
  ],
  "retired": ["cw-uk-004"]
}
```
Клиент хранит `manifestVersion`, фильтрует по `schemaVersion ≤ поддерживаемой`, `minAppVersion ≤ versionCode`, языку интерфейса.

Конверт пакета:
```json
{ "schema": 1, "packId": "…", "category": "MINI_CROSSWORD", "language": "uk", "packVersion": 3,
  "puzzles": [ { "id": "cw-uk-x-000123", "contentVersion": 1, "difficulty": 2, "payload": { } } ] }
```
Ошибки: HTTP 304 (не изменено), 404 (пак снят), 5xx/таймаут → повтор с экспоненциальной паузой; несовпадение sha256 → отбросить, оставить прежнюю версию.
Опционально `GET /v1/updates?…` (Functions) — только если понадобится серверная фильтрация; защищён App Check.

JSON Schema по категориям (Draft 2020-12; `additionalProperties: false`; версия в `$id`):
- `number_sequence.v1`: `prompt:string`, `sequence:int[3..12]`, `answer:int`, `explanation:string`, `hints:string[]`, `difficulty:1..100`. (повторяет `NumberSequencePuzzle`).
- `matchstick.v1`: `startMask:int 0..2^23-1`, `maxMoves:1..3`.
- `word_logic.v1`: `type ∈ {ODD_ONE_OUT, ANALOGY, PAIR, COMMON_CATEGORY, SEQUENCE}`, `stem`, `options[4]{id,text}`, `correctId`, `hint`, `explanation`, `language`.
- `mini_crossword.v1`: `size`, `entries[]{row,col,direction∈{ACROSS,DOWN},answer,clue}`, `language`.
- `visual_logic.v1`: `rule`, `columns`, `gapIndex`, `tiles[]`, `options[4]`, `correctId`; `Tile{kind,color,rotation∈{0,90,180,270},count,slot∈-1..3}`.
- `word_search.v1`: `size`, `letters(size²)`, `placements[]{word,path[]{row,col}}`, `language` (или `dictionary.v1` для режима «словарь»).
- `sudoku.v1`, `orb_lines.v1`, `two_dots.v1`: зарезервированы; нужны только если принято решение о внешних стартовых позициях (❓).
Каждая схема: пример валидный/невалидный будет добавлен на Этапе 2.

## 14. Публикация и синхронизация

1. Publisher собирает `Approved` задания категории/языка → пак `N+1` (иммутабельный), считает sha256, пишет в Storage, затем документ `packs/`, затем **последним** обновляет `manifest.json` (атомарный переключатель).
2. Откат: манифест снова указывает на предыдущий `packVersion`; ранее скачанные клиентом пакеты не удаляются.
3. Отзыв задания: ID попадает в `retired[]`; клиент не выдаёт его **новым** игрокам, у уже решивших остаётся в `solved_puzzles`.
4. Правка содержимого = новый `contentVersion` **и** новый ID, если меняется смысл/ответ (ID не меняет смысл).
5. Миграция схем: `schemaVersion` повышается, старые клиенты продолжают получать пакеты старой схемы (2 параллельные ветки на переходный период).

## 15. Офлайн-стратегия

- Встроенные паки/генераторы остаются; загруженные — добавляются **после** встроенных (не ломая индексы).
- Скачивание: WorkManager (unmetered/любая сеть по Remote Config), проверка sha256 и JSON-схемы **до** активации; запись во временный файл, затем атомарный rename; ошибка → прежний пак остаётся.
- Текущая игра не зависит от сети. Манифест проверяется не чаще интервала Remote Config.

## 16. Совместимость с XP и сохранениями

- `puzzleId` — ключ XP-идемпотентности; ID иммутабельны, формат внешних: `<prefix>-<lang?>-x-<NNNNNN>` (суффикс `x` отделяет от встроенных `cw-uk-01`).
- Для категорий с индексом (WordLogic/Crossword/Visual) клиенту нужен переход на `firstUnsolved` по ID (как в Matchstick/NumberSequence) или формулу «встроенные N штук → затем внешние по orderIndex» (индекс не ломается, пока встроенный список неизменен).
- Состояние `encode()` ссылается на `puzzle.id`; пакет должен хранить задания, пока на них есть незавершённое состояние (клиент не удаляет паки с активными состояниями).
- XP остаётся локальным. Серверной синхронизации прогресса нет (отдельный этап c Authentication).
- Daily: ID `…-d-yyyymmdd`, идемпотентный ключ XP — см. §1d; в клиенте не реализован, сейчас XP только в CAREER.

## 17. Безопасность

| Компонент | Доступ |
|---|---|
| `public/v1/**` в Storage | чтение всем; запись — никому из клиентов |
| `private/**`, Firestore | клиентам запрещено (Rules `allow read, write: if false`); доступ — сервисные аккаунты |
| Админ-callable | IAM + custom claim `admin`, App Check |
| Cloud Run Jobs | отдельный сервисный аккаунт на job, минимальные роли (Storage objectAdmin на нужный префикс, Datastore user) |
| Секреты | Secret Manager, не в репозитории и не в APK |
| Клиент | App Check (Play Integrity), без ключей записи |

Ввод: все внешние данные — только через схемы; парсеры без исполнения кода; лимиты размера, таймауты, allow-list доменов.

## 18. Оценка расходов (требует проверки по официальным тарифам)

**Точные тарифы и квоты здесь не приводятся** — актуальных данных в сессии нет. Перед запуском проверить: условия плана Blaze и бесплатные квоты; Cloud Storage (хранение, операции Class A/B, исходящий трафик); Cloud Run Jobs; Cloud Scheduler; Cloud Functions 2nd gen; Firestore; Secret Manager; Cloud Billing Budgets. Blaze не гарантирует отсутствие расходов — это тариф с оплатой по факту, поэтому бюджетные уведомления обязательны.

**Допущения (явные):** 20 запусков приложения в месяц на пользователя; манифест проверяется не чаще 1 раза в сутки (условный GET по ETag, ≤30 запросов/мес; ответ 304 ≈ <1 КБ, 200 ≈ 3 КБ); пакет ≈ 40 КБ gzip (реальный размер будет измерен на этапе B); обычный пользователь скачивает ~4 пакета/мес; первая установка — ~7 пакетов своего языка (~280 КБ); Firestore клиентами не читается; генерация — 1 запуск Cloud Run Job в неделю.

| Активных пользователей | запросов манифеста/мес | скачиваний пакетов/мес | исходящий трафик/мес (оценка) | Firestore reads от клиентов |
|---|---|---|---|---|
| 1 000 | до 30 тыс. | ~4 тыс. | ~0,2 ГБ + новые установки | 0 |
| 10 000 | до 300 тыс. | ~40 тыс. | ~1,6 ГБ + новые установки | 0 |
| 100 000 | до 3 млн | ~400 тыс. | ~16 ГБ + новые установки | 0 |

Вывод: на 1 000 и 10 000 пользователей расходы определяются в основном фиксированными частями (Cloud Run Job раз в неделю, Scheduler, Secret Manager) и, вероятно, малы или в бесплатных квотах (**проверить**). На 100 000 основная статья — исходящий трафик Storage (десятки ГБ): снижается gzip, immutable-кэшем, ETag/304, редкими обновлениями, дельта-пакетами и при необходимости CDN. Daily добавляет ~7 небольших файлов (несколько КБ) на пользователя в неделю — пренебрежимо. Меры: бюджетные алерты (например 50/90/100 % месячного лимита, сумму задаёт владелец), мониторинг egress и числа запусков Job, отсутствие генерации при открытии приложения.
